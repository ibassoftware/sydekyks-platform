# Inactive hosted onboarding and accounting backend

This branch adds backend services, authenticated hosted routes and a first worker-broker integration. Hosted API and worker startup still fail with `HOSTED_IMPLEMENTATION_INCOMPLETE`; workers still advertise accounting protocol zero. Integration tests exercise the routes and broker in isolated test harnesses. No deployed signup, outbox consumer, managed provider traffic, Stripe client or payment grant issuer is enabled. Self-hosted signup, authorization, provider billing and free access keep their existing behavior.

## Tenant lifecycle

`createHostedOnboarding` requires a database with the immutable hosted installation marker. Provisioning locks a verified identity, durably claims normalized-email trial eligibility, creates the Platform, owner membership, personal Project, trial account and two grants, and records an outbox event in one transaction. A retry by the same identity returns the existing tenant without renewing its trial. An existing active hosted member is directed to their existing tenant rather than receiving another trial. Expired tenants remain selectable for account recovery but cannot admit new work.

Trial eligibility is an HMAC of the normalized email, with a separate durable identity claim. The HMAC secret must be stable and at least 32 characters; its fingerprint is pinned in `hosting_policy`. These tombstones deliberately have no identity/Platform foreign keys. Deleting and recreating an identity does not restore eligibility. Secret rotation requires an explicit migration; silently changing it fails closed. Email aliases and multiple real identities require further abuse controls before signup activation.

Invitations store only a SHA-256 token digest and subject HMAC. Only the addressed verified identity may accept. Invitations reserve an active seat and the actual new-Project delta, including reuse of a deactivated member's retained Project. Account and Platform locks serialize invitation creation, acceptance, revocation and role changes. Members retain the existing personal-Project isolation rules; being invited does not make them an administrator. Owner removal/demotion is forbidden. Role/removal changes rotate identity token versions, revoke persisted MCP grants and record an outbox event.

Hosted HTTP adapters derive identity, tenant and session version from the authenticated principal. They provision through the transaction service and mint tokens only against its committed session-version receipt; a concurrent revocation cannot mint a newer replacement session. Hosted anonymous requests never select the oldest Platform. Hosted signup does not use CE automatic email verification or legacy invitation auto-provisioning. Tenant switching rechecks active membership and the originating session version. Legacy Platform/member/Project creation and membership mutation services refuse hosted writes, and the legacy invitation module is not registered there.

The hosted-only `/v1/hosting/verify-email` endpoint verifies an existing one-time email-verification code using the existing distributed guess budget. It requires a password established by the inbox owner at verification time, replaces the password chosen before inbox proof, rotates the session version under an identity row lock and then provisions/onboards the verified identity. Verified identities cannot reuse this endpoint as a password-reset route. `/v1/hosting/verification-code` provides rate-limited resend/recovery for unverified identities, reusing existing OTP lifetime and identity-wide guess budgets and returning the same empty response for absent/verified identities. Consuming a proof followed by a failed database write does not strand signup: another code can be requested. Existing self-hosted password routes and the absence of self-hosted passwordless routes are unchanged. SMTP is mocked in tests; hosted email delivery configuration and abuse-control acceptance still precede activation.

The other `/v1/hosting` routes provide authenticated invitation creation/revocation/acceptance, member changes and serialized balances. Request bodies cannot choose the acting identity or tenant. Existing onboarding completion and Platform creation routes call the hosted transaction service only for hosted mode. A stale onboarding request fails even if provisioning already committed; recovery requires fresh authentication. Hosted MCP authentication checks the persisted grant, its tenant/user/Project binding and current verified membership, in addition to the existing cache checks. Grantless internal MCP tokens are refused in hosted mode pending a scoped gateway replacement. Existing websocket verification rechecks the token and Project permission on each user event; this package does not claim a full live-socket isolation/recovery acceptance matrix.

## Ledger units and state transitions

Execution grants use whole execution units. Managed AI grants, reservations, ledger amounts and operator budgets use **integer micro-USD**, represented by TypeScript `bigint` and PostgreSQL `numeric(30,0)`. The meter identifies the amount's unit. The balance result explicitly returns `unit` and, for managed AI, `microcreditsPerUnit = 1000`. Serialize bigint values as decimal strings at an eventual HTTP boundary; never convert financial quantities to floating-point numbers.

The proposed trial grants are 1,000 executions and 1,000,000 micro-USD. The latter equals 1,000,000,000 microcredits, or 1,000 displayed credits, representing at most USD 1 of managed cost. This is separate from the unchanged legacy `AP_AI_CREDIT_USD_VALUE` conversion. Trial lifetime is 14 days. All plans permit BYOK; BYOK execution admission consumes execution units and concurrency but never managed AI credits. Trial expiry blocks hosted BYOK work as well as managed work.

An execution reserves one unit and a concurrency slot. Claiming it once produces a random dispatch fence, consumes the execution unit and marks it running. Completion releases the slot without refunding a started execution. An unsent reservation may be released once. `cancelUnsent` is a trusted reconciliation operation that can clean up reserved work after membership removal. It must never be exposed as an unauthenticated or tenant-supplied accounting endpoint.

Each managed call reserves its maximum cost against its original grant and the global admission-day UTC budget. The original running execution binds its tenant, Project, actor and grant source/period. Its legacy payer field remains a provisional managed-capability marker; the gateway independently binds actual credential ownership and payer on each model call. A later plan change cannot move that execution onto a new period. A still-unsent reservation from an earlier UTC day releases at claim and cannot dispatch; only the trusted orchestrator may create a fresh attempt key against today after observing that durable unsent outcome. Running and uncertain attempts retain their original day. A second claim cannot dispatch a running, uncertain or settled reservation. Once dispatch may have occurred, uncertainty retains the full reservation and prevents a duplicate dispatch or refund of that attempt. A bounded explicit gateway retry has its own ordinal, fence and additional reservation; it never releases the earlier uncertain liability. Root completion waits for every child liability to settle or release.

Settlement validates the random dispatch fence and updates the original grant/day, including after entitlement expiry, midnight or membership removal. Identical settlements are idempotent; conflicting actual amounts fail. A cost exceeding its bound is recorded as actual liability and suspends the account instead of rolling back the charge record. Ledger rows reject UPDATE and DELETE at the database level. Reserved/consumed projections and immutable entries are written in the same transaction.

All execution/call keys must come from stable server-generated root and logical-call identities, rather than fresh keys per queue retry. Admission and claim require current verified membership and Project write access. Completion, uncertainty and trusted cancellation are internal adapters: tenant IDs, dispatch fences and authoritative provider costs must come from persisted worker/gateway context. They are not public request fields. Provider SDK automatic retries must remain disabled unless each send is separately reserved and identified.

The global lock order is daily budget, then account, followed by dependent records. Onboarding may lock identity before account and Platform; ledger membership reads do not lock identities. Database wall-clock time is read after admission locks, so a transaction waiting past expiry cannot admit work based on its start time.

## Segments, nested execution and crash recovery

The coordinator persists each worker delivery as a segment in `hosting_dispatch`. Independent BEGIN flows and CHAT roots establish the root; waitpoint resumes and authenticated nested flows attach to it. The single root reservation retains the original grant, actor and execution charge. A resumed segment does not reserve or consume another execution unit. Reacquisition checks current membership/session, entitlement, original grant validity and available concurrency; a renewal never replaces an expired original grant.

Only one segment per root may be admitted/running/uncertain at once. Nested work can be prepared while its parent runs, but waits until the parent's fenced pause/completion join. Fire-and-forget children wait for parent completion. A root parks and releases its slot only when no active segment or outstanding managed liability exists. Reconciliation considers the newest generation of every run and all prepared descendants; it settles only after every run resolves. A cancelled unsent child/resume does not refund an already-started root. Root preparation is capped at 128 segments, ancestry at eight flow runs, and each stored job/checkpoint at 1 MiB.

Hosted engine tokens carry a routing hint for the optional `RunContext.callSubflow` adapter. Call Flow and Stream CSV use `/v1/engine/nested-runs` in hosted mode; the self-hosted webhook implementation stays on its existing branch. The server authenticates the engine principal, derives parent/root/tenant/Project/actor from its exact live admission, checks access and a published callable flow in the same Project, and atomically creates the child run plus dispatch intent. Deterministic invocation keys include the engine step/loop path and CSV batch index. Exact retries return the same child; changed payloads conflict. Callback URLs must identify a waitpoint owned by that parent segment. Public webhook parent headers cannot establish hosted inheritance. Failed nested runs and unsent denials durably complete their bound parent's pending waitpoint with an error signal.

A hosted pause requires the exact awaited waitpoint, its source segment, and a matching owned log file. The callback copies a bounded execution-state snapshot into the durable segment. Engine and worker callbacks use exact admission IDs; a socket connection alone never selects a segment. The latest generation fences the synchronous run status/log projection, replacing legacy asynchronous metadata projection for hosted callbacks. A resume atomically consumes that source waitpoint and creates its next segment, retaining a durable source key after consumption. The engine loads the stored checkpoint through a running-admission-scoped endpoint and writes to a fresh segment log ID. Old waitpoints and callbacks cannot update a newer generation. Hosted waitpoint expiry uses a generation-fenced coordinator resolution, preserving the original pause receipt and signaling a waiting parent.

Prepared segments store their queue, stable job ID, normalized payload and availability time before Redis publication. A hosted-only sweep is wired after queue initialization, every 30 seconds, in bounded batches. It republishes only SQL-proven unstarted work after a missing/failed queue delivery, reuses reservations, revokes expired unstarted admissions, and reconciles completed/paused roots after late child settlement. Historical settled roots are excluded. Blocked waitpoint signals rotate fairly rather than permanently occupying the oldest batch. This is at-least-once publication; the durable admission/start fence prevents repeated execution.

Worker heartbeats extend the durable lease only after a valid BullMQ lock extension. Expired started leases and disconnects become uncertain; missing Redis state or elapsed time never proves that side effects did not happen. Started work is never replayed or refunded automatically. Exact durable terminal/completion receipts can reconcile uncertainty; missing outcomes require further operator/provider evidence. Uncertainty ledger entries use the root reservation and segment identity so a later uncertain segment cannot collide with an earlier resolved episode. Accounting still commits before Redis acknowledgement. The recovery timer remains unreachable in a normal hosted startup because the bootstrap hard stop is unchanged.

Hosted root cancellation and explicit same-run retry remain refused pending their own policy. Trigger/poll/repeating work, unbound worker submissions, remaining Syd/MCP/tool/background paths remain gated. Legacy bare resume links cannot supply a hosted waitpoint binding. Legacy dispatch records without persisted payload/checkpoint/lease evidence are not inferred to be safe to replay. Hosted bulk file deletion is temporarily disabled and explicit deletion refuses files in Projects with open execution reservations, protecting checkpoint slice/payload references; bounded reference-aware retention and cleanup remain activation requirements. Hosted status projection is minimal; the remaining metadata/UI/notification outbox is not supplied by this change.

## DeepSeek gateway and BYOK

The fifth inactive package adds `/v1/engine/hosting-ai/chat/completions` and a native text-step adapter at `/v1/engine/hosting-ai/step`. Both require the exact authenticated running admission, current segment generation, unexpired lease, verified actor/session and Project write access, an active account and the original active execution grant. CHAT admissions additionally recheck the persisted active conversation run. Tenant, Project, actor and root are derived from that admission; clients cannot nominate a different reservation. The optional `RunContext.callAi` adapter routes hosted Ask AI, Summarize Text and Classify Text steps through this gateway. Self-hosted steps keep the existing synchronous/waitpoint route.

Each call declares either managed payment or one exact DeepSeek BYOK configuration ID. There is no fallback to another key or payer. A root can contain both types. Every catalog plan, including the limited trial, permits BYOK without consuming managed allowance; BYOK still requires an admitted execution and active hosted entitlement. Trial expiry blocks both. The legacy root payer label is not used to select credentials or charge BYOK. Native steps support `deepseek-flash`, text messages and non-streaming completion only; the raw authenticated gateway also permits bounded function declarations and JSON output. Function declarations do not execute tools or authorize external side effects.

The endpoint is fixed to `https://api.deepseek.com/chat/completions`, thinking is explicitly disabled, and arbitrary base URLs, headers, redirects, remote content and provider retries are refused. Requests are limited to 64 KiB, responses to 2 MiB, output to 4,096 tokens and provider timeout to 60 seconds. A root has at most 32 persisted model attempts and one prepared/running send at a time; an uncertain attempt retains liability while a separately reserved explicit retry may proceed. Each logical call permits ordinal zero and at most two explicit retries. The native adapter sends only ordinal zero and does not retry automatically. Other providers, models, images/files, web search, extraction, streaming, router fallback and remaining chat/title/compaction/background paths are blocked pending scoped gateway integration. The DeepSeek protocol and model were checked against [official chat completion documentation](https://api-docs.deepseek.com/api/create-chat-completion/) and [thinking-mode documentation](https://api-docs.deepseek.com/guides/thinking_mode/); this package makes no provider request.

`hosting_model_call` persists the segment/admission, actor, root, logical key/ordinal, canonical request hash, payer, exact credential fingerprint, model/endpoint, quote, managed child reservation, dispatch fence, lease and observed outcome. Account locking serializes prepare/send and hosted credential mutations. Credential material and model/Project scopes are rechecked immediately before the durable send claim, including the encrypted material fingerprint and session version; changes invalidate prepared work. Credential revocation after that claim cannot retract an already claimed send. Settled identical replays return the recorded bounded response; changed requests or keys conflict. Prepared work can be canceled as known unsent. A running claim is never automatically resent, including after process failure. Recovery marks expired running calls uncertain and keeps both managed liability and the root slot. BYOK calls are tracked durably too, so unresolved BYOK work also blocks parking/terminal release.

Managed credentials come only from `AP_HOSTED_DEEPSEEK_API_KEY` on the API server. BYOK credentials are encrypted in the existing provider table and decrypted only by the server gateway. Hosted provider CRUD accepts DeepSeek only, validates syntax locally without a billable probe, and returns metadata with `credentialValidation: not_probed`. Every mutation takes the same tenant account lock and rechecks current administrator membership/session. Selected Projects must belong to the tenant. A key's exact ID, active state and model/Project scope are checked for every send. Hosted legacy key resolvers, model/router fallbacks, provider probes and worker-reported usage/outcome billing are refused; workers, pieces and browser callers never receive provider secrets. The metadata adapter serves authenticated users and returns only the local supported model and managed tier, without provider calls. Generic engine/editor option jobs still have no admitted execution and remain gated; end-to-end hosted editor options, key-management UI and disabled-feature presentation remain outstanding. The native text adapter supports already configured, valid admitted flows; it does not claim complete hosted authoring UI support.

There are no default managed prices. `AP_HOSTED_DEEPSEEK_PRICE_JSON` must contain an operator-reviewed quote with `version`, `model: deepseek-flash`, UTC `validFrom`/`validUntil`, `rates` and `ceiling`. Both price objects contain integer `cacheHit`, `cacheMiss` and `output` values in **micro-USD per million tokens**. Quote windows may be at most one hour and must retain the full timeout plus five seconds before dispatch. The approved ceiling must cover **every applicable provider tariff**, including peak pricing and any change that could apply during a request, regardless of the cheaper settlement rates. It is trusted server policy, never request input. DeepSeek publishes time-dependent tariffs in its [official pricing documentation](https://api-docs.deepseek.com/quick_start/pricing/); checking the quote against the applicable tariff schedule is required operational acceptance before activation. A response timestamp alone cannot prove a tariff. The server requires its entire send-to-settlement interval and observed response creation to lie inside the approved window; otherwise it retains uncertainty.

To avoid an unproven tokenizer estimate, each managed send conservatively reserves the complete 1,048,576-token context at uncached ceiling cost plus the requested maximum output. This intentionally reduces usable trial calls until a separately verified tighter input bound is implemented. Admission uses the original managed grant and global UTC-day budget, with daily-budget then account lock order; day changes cannot create a reversed lock order. Settlement uses only gateway-observed, internally consistent prompt/cache/output counts, rounding up integer micro-USD. Cost settlement and the recorded response commit together. Unexpected HTTP outcomes, missing/invalid usage, transport failure, uncertain tariff or lost settlement evidence retain the full bound; elapsed time never refunds it. Actual cost beyond the bound is recorded and suspends the tenant. No public endpoint accepts cost, fence, refund or reconciliation evidence.

Self-hosting remains free and uses its original execution, resume, retry, nested-flow, callback, retention, provider identities and legacy credit conversion. Hosted bootstrap and worker protocol zero remain unchanged; none of these new routes can enable normal hosted startup.

## Stripe test billing backend

The sixth inactive package adds admin-authenticated `/v1/hosting/billing`, `/checkout` and `/portal` routes plus a public signed `/stripe-webhook` endpoint beneath that prefix. Checkout accepts only `starter` or `team`; browser input cannot select amounts, prices, customers, subscriptions, entitlements or return URLs. Expired trial owners can purchase or open recovery tools without reopening a trial. Self-hosted mode registers none of these routes and never constructs a Stripe client. Hosted startup remains blocked, so these source adapters do not enable a payment flow.

The API directly pins Stripe SDK `18.2.1` and API `2025-05-28.basil`, reusing the SDK version already in the source dependency graph. The SDK is imported lazily for hosted billing only, with automatic network retries disabled and a 15-second request timeout. Test-key syntax, returned object mode and the current account ID are checked. Connect events and unexpected API versions are refused. There is no live-key path.

`AP_HOSTED_STRIPE_CATALOG_JSON` is mandatory when constructing the adapter. It contains the exact shared catalog `version`, Stripe `accountId`, `portalConfigurationId`, application `origin`, and `plans.starter` / `plans.team` objects. Each plan has a distinct `priceId`, positive integer `amountMinor` and lowercase three-letter `currency`; both plans use the same currency. There are no default prices or Stripe objects. The origin must be an exact HTTPS origin or loopback HTTP origin, with no user information, path, query or fragment. Server-built return URLs target `/settings/billing`; that hosted UI is still outstanding. A canonical catalog hash is pinned to each binding and command; changing it requires an explicit catalog migration rather than silently reinterpreting existing purchases. A configured price must currently be active, fixed monthly licensed pricing, quantity one, with the exact approved amount/currency and no quantity transform. Tax/merchant configuration and current SDK/API support acceptance remain prerequisites to activation.

The additive binding and command tables serialize one outstanding purchase per tenant. Selected-plan user/Project limits, including pending invitations, are checked before prepare, dispatch and URL delivery and again at entitlement activation; incompatible purchases fail before a new Checkout is created. Every external create has a durable canonical payload hash, stable idempotency key, initial send time and claim fence before network access. Customer creation is separately durable; Checkout cannot substitute an email match for its bound customer. Explicit retries use the same payload/key within a 23-hour horizon. Expired or uncertain commands are not replaced with a fresh create key merely because time elapsed. A ready Checkout is replaced only after Stripe confirms expiration; a completed purchase waits for reconciliation. Results commit before a separate current administrator/session check permits delivery of fresh or cached bearer URLs, so revocation during a Stripe request does not expose its result. Portal sessions require a pinned active test configuration with payment-method updates and invoice history enabled, subscription updates disabled, and cancellation only at period end without proration. The Portal response reports a five-minute application delivery window, not a promise that Stripe revokes an already delivered URL at that instant. Portal configuration must remain under controlled operator ownership. Plan changes, discounts, overages, top-ups, annual billing and prorations are not supplied by this slice.

The raw-body webhook route limits payloads to 256 KiB, verifies the Stripe signature with a five-minute tolerance, and records the verified event identity, semantic hash, raw-byte hash and routing metadata before acknowledging it. The direct-account endpoint context supplies the configured account partition when normal events omit an account field. Duplicate event receipt and logical-period grant creation are separate deduplication boundaries. Changes to immutable event data conflict, while volatile delivery counters do not change its semantic identity. Supported events schedule reconciliation; unsupported valid events are retained as ignored. Stored customer/charge routing avoids requiring an old Event object to remain retrievable. Unbound customers are quarantined; webhook snapshots and browser success redirects never grant service. These boundaries follow [Stripe webhook guidance](https://docs.stripe.com/webhooks) and [idempotency guidance](https://docs.stripe.com/api/idempotent_requests).

A separate hosted billing timer processes bounded inbox and account batches without blocking execution recovery. Reconciliation claims a lease/fence before any Stripe reads, performs network calls outside SQL locks, then rechecks its fence and notification revision under the account lock. Empty, leased and failed bindings move out of the oldest due batch. An older response cannot replace a newer projection or clear a newly received risk hold. Polling and temporary Stripe outages do not suspend an independently verified paid entitlement or extend its dates. Read failures are recorded separately from admission holds. A pending verified dispute is an account-wide risk; a full-refund notification for a locally proven expired funded period does not hold a different paid current period. New financial authority still requires current provider evidence.

Current subscription, customer, one exact logical subscription item, catalog price, quantity, currency, full non-prorated invoice line period and successful full card payment are checked before issuing paid grants. Basil item-level periods and invoice parent/pricing/payment objects are used; the adapter does not assume older top-level period or invoice-subscription fields. Subscription metadata must bind the purchase to its durable tenant command. Duplicate active subscriptions, overlapping paid periods, reused invoice lines/payments and unapproved plan changes are quarantined. A logical source derived from account, accepted subscription/item and period creates one execution and one managed grant; replacement invoice IDs add supporting evidence and cannot mint another allowance. First current paid activation revokes the unused trial grants without resetting eligibility. Historical/future dates retain their original bounds and cannot become a new present-day allowance. Existing reservations retain their original grant and provider budget day. Managed paid grants use the existing hosted cost conversion; all catalog plans retain BYOK without managed debits.

Refunds and disputes are reconciled against captured charges linked by verified invoice payments. Cumulative succeeded refunds must match the charge's refunded amount. A full refund or lost dispute revokes only its funded period; partial refunds retain limits pending commercial adjustment. Each open dispute contributes an independent hold. Winning one cannot clear another or restore an independently suspended account. Account `billingHold` is separate from the existing security/cost `suspended` status; billing never clears the latter. Grant `revokedAt` blocks reserve, claim, resume and gateway use, while already-sent liabilities can settle. Revocation leaves original quantities, dates, usage and reservations intact, records compensating unused-authority entries, and records further compensation when a revoked reservation releases unused capacity. Ledger history remains immutable.

This slice reconciles `subscription.latest_invoice` plus charges of previously recorded periods. It does not reconstruct every missing historical invoice or payment after multiple missed renewals. It refuses incomplete pagination, split payments, credit-note/discount/proration noise and unsupported subscription shapes. History is bounded to 128 periods/charges with per-read timeouts and a history-read deadline; larger histories need partitioned reconciliation and retention policy. Unknown create outcomes beyond the idempotency horizon require audited operator reconciliation; no operator refund/retry UI is supplied. Deferred runtime checks must cover PostgreSQL races, malformed/reordered webhooks, paid/trial transition during active work, refund/dispute boundaries, outages, credential/session changes, catalog changes, all supported SDK response shapes and fresh installs. Full historical recovery, hosted billing UI and broader commercial lifecycle acceptance remain unfinished. No migration, Stripe object, payment, provider request, deployment or automated test is performed by this source package.

## Migration and validation

`SydekyksHostingLedger1882000000000` adds nine hosting tables and the immutable-ledger trigger. `SydekyksHostingDispatch1883000000000` adds the durable dispatch table and refuses rollback when it contains records. `SydekyksHostingSegments1884000000000` adds nullable segment/recovery/checkpoint fields, expands reservation states with `paused`, and adds a nullable source-dispatch binding to waitpoints. It refuses rollback with dispatch evidence or paused reservations. `SydekyksHostingModelCalls1885000000000` adds the per-call gateway evidence table with same-tenant foreign keys and unique logical attempt identity; its rollback refuses any recorded call. `SydekyksHostingStripe1886000000000` adds four billing-evidence tables, a default-false account billing hold and nullable grant revocation time; rollback refuses retained Stripe evidence or holds/revocations. These migrations neither backfill tenants nor rewrite existing product/provider records. An empty-table rollback locks the hosting tables and removes only that schema; any hosted financial, policy or eligibility data prevents rollback. Back up and explicitly plan audit-preserving migrations rather than dropping billing evidence.

Integration tests use actual isolated PostgreSQL schemas for races, rollback, tenant access, trial replay/expiry, invitation capacity/reactivation, dispatch fences, credits, uncertain liabilities and settlement. PGlite tests cover additive migration round trips, preservation of existing identity data, bigint transformation and ledger immutability. Existing free-access, authorization and hosted-startup refusal tests remain required. These checks do not replace the full deployed-image upgrade matrix.

For the segment/recovery, gateway and Stripe packages, automated suites and CI changes are deferred at the user's request. Validation is limited to local builds, focused lint, source/distribution checks and Astra source review. The explicit engine typecheck retains nine diagnostics also reproduced against the baseline source; no new diagnostic remains. The normal engine build bundles rather than typechecks. No database migration, crash-injection or deployed-image upgrade acceptance is claimed for this package.

Before hosted runtime can be enabled, complete the deferred segment/recovery tests and source-to-runtime acceptance; reference-aware retention, operational handling of blocked/uncertain work and root cancellation/retry policy; hosted signup/usage UI, email and abuse-control acceptance; admission across all remaining Syd, MCP, tool, trigger and background cost paths; remaining side-effect outbox publication and broader crash reconciliation; gateway runtime/migration/concurrency/fault acceptance, approved tariff operation and tighter input-cost bounds, streaming and remaining provider adapters; Stripe runtime, historical reconciliation, commercial-policy and billing UI acceptance; and the plan's isolation, recovery, fairness and upgrade acceptance gates. Prices and paid grants cannot come from client-supplied plan state. Live billing and deployment require separate user authorization.
